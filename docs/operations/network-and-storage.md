# 网络与资源上传下载

## 当前可用的三条资源路径

| 用途 | 路由族 | 内容与上限 | 可读范围 |
| --- | --- | --- | --- |
| 旧式JSON资源 | assets / manifest / file | files字典整体替换，2MiB请求；canonicalJson哈希 | **所有已登录账号** |
| 世界公开版本 | publication / blobs | 最多301文件，其中一份table.json≤2,000,000字节；附件最多300个、单个≤64,000,000字节 | 当前GM与成员；仅当前清单中的哈希 |
| 共享媒体库 | media / media/file / media/blob | 单个≤32,000,000字节、清单合计≤512,000,000字节 | 当前GM与成员 |

以上“公开版本”是世界成员可见的投影，不表示向互联网公开。完整GM世界备份保存在主持人设备；若使用GM snapshot端点，只允许该世界GM读写，但服务器本身不验证其中的游戏内容。

媒体库目前检测 PNG、JPEG、WebP、GIF、SVG、MP3、OGG、WAV、WebM、MP4、PDF 文件头，不支持 GLB。公开版本附件支持GLB等清单格式，见 [上传API](../api/http.md) 和 [导入格式](../authoring/formats.md)。不同管线的允许类型与大小不能混用。SVG响应有受限内容策略；不能把脚本网页伪装成素材。

## 正确的发布顺序

1. 本地完成模型解析、规则身份核对、资源依赖检查与玩家投影检查。
2. 给最终字节计算SHA-256和size；压缩、裁剪或转码后必须重算，不能复用旧哈希。
3. 上传缺失blob，检查状态码；upload成功不代表已经完成一次世界发布。
4. 携带expectedVersion提交清单。服务器检查身份、文件、投影及资产一致性，成功才原子切换当前清单。
5. 冲突409先重新读取版本并核对；下载端只请求当前获准清单的哈希，验证长度与散列后使用。

publication的文件上传是流式写入并核验哈希；共享media当前仍采用内存缓冲，并且下载前可能读全文件校验。不要把任一端点误认作已有断点续传、多段上传或大型视频分发服务。

## 先做的网络优化

- **靠近玩家部署。** 选择实际玩家可直连的地区及域名，客户端与部署工具优先本地缓存、直连访问。不能承诺由工具控制所有设备的VPN/TUN路由。
- **控制素材尺寸。** 地图、token、立绘分开；保留原稿，分发经过确认的展示版本。音频循环按用途压缩。内容变化才改变哈希，避免每次进场全量下载。
- **稳定信令。** HTTPS/WSS同域，反代正确转发升级请求与长连接。排查证书、来源、会话过期、成员关系，再检查ICE；不要把所有连接问题归咎于素材服务器。
- **优先WebRTC直连。** 同网或NAT可穿透时节约服务器流量；连接不通需要TURN兜底。TURN会承载中继流量，需单独预算带宽、连接数及滥用防护。[WebRTC官方TURN说明](https://webrtc.org/getting-started/turn-server)
- **减少重复元数据。** 利用现有投影、哈希缓存和合集按需请求；不要在聊天或战斗帧内base64嵌入整张地图。

ManualConnection已支持构建时VITE_ICE_SERVERS，AAF连接尚未统一接线。共享网络库可以接收RTCIceServer[]，但短期凭据签发、运行时配置发现、多节点探测仍需开发。不能将长期TURN密码写入公开VITE变量或安装包。

## 当前能否直接用CDN或对象存储

当前Node服务从DATA_DIR提供素材，不存在S3配置变量、预签名URL端点或分片上传协议。可以用反代托管**单独公开发行的安装包**；受成员权限保护的世界素材不能直接挂成公共静态目录。

建议下一阶段实现如下分层，明确它是方案而非现有API：

| 后续组件 | 行为 | 必须保留的约束 |
| --- | --- | --- |
| 素材授权服务 | 校验世界成员，签发短时下载地址 | token不进入公开URL日志；离开世界后不能长期沿用授权 |
| 对象存储 | 使用内容哈希键；应用数据库记录引用 | 上传后验证实际大小、类型与hash；文件不可被同键静默覆盖 |
| CDN | 缓存不可变字节 | 签名或边缘鉴权；私密资料不进公共缓存 |
| 上传会话 | 大文件分块、重试、进度与完成校验 | 预留配额、超时清理、提交清单前确认完整 |
| 回收任务 | 清理不再被任何有效版本引用的blob | 宽限期、备份／保留版本、dry-run清单、恢复手段 |
| 审计与限额 | 每账号／世界／日流量／并发配额 | 不记录密码、令牌或私密文档正文 |

目前publication没有完整的世界总配额，删除世界也不会自动清理media/publications目录，上传中断可能留下未引用文件。因此初始运营应监控磁盘和下载流量；启用自动回收前先补引用追踪，不能用“旧于若干天”直接删哈希文件。

## 监控与容量判断

分别记录API延迟、5xx/429/409、信令在线数与重连率、WebRTC建立耗时及直连／中继比例、每世界素材大小、上传失败率、下载带宽、进程RSS、state.json大小与持久化耗时、磁盘剩余量和备份恢复耗时。当前没有内置Prometheus端点，这些需要部署监控或后续埋点。

扩容顺序应由实测瓶颈决定：先减少素材重复传输，再改善静态分发；状态写入成为瓶颈时，设计可事务持久化及共享信令／会话路由，然后才做多副本。仅在负载均衡后放两份当前文件服务不受支持。
